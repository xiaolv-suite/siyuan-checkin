# 事项删除、停用、跨窗口墓碑与关联隔离规范（T-1721 / D-633）

> **研究与规范背景**：承接 T-1622 残留的跨窗口删除同步问题。明确“停用/永久删除”的用户语义，确立基于 `OccasionTombstone` 的跨窗口防复活机制，规范墓碑容量治理，并严格界定事项删除与主打卡项目事实的隔离边界。

---

## 一、用户操作语义消歧

在事项系统（`Occasion`）中，用户对不需要的事项存在两种截然不同的诉求：

1. **停用（Disable，`enabled: false`）**：
   - **语义**：暂时不生效。例如：由于工作变动，某项每季度的检查暂时暂停；
   - **行为**：保留在 `occasions` 列表中，全部历史完成记录（`completedDates`）与单次实例改期（`overrides`）100% 完整保留；
   - **投影影响**：不出现在 Today 横幅和即将来临列表中，不触发待办提醒；
   - **复苏**：随时点击播放（play）图标即可重新启用，不产生任何数据丢失或新实体；
   - **墓碑影响**：**绝对不生成墓碑**。
2. **永久删除（Permanent Delete）**：
   - **语义**：该事项已被用户确认彻底移除；
   - **行为**：从 `store.occasions` 列表中物理剔除，并在 `store.tombstones` 中原子记录 `{occasionId, deletedAt}`；
   - **防复活不变量**：旧窗口或多窗口并发交错时，若旧窗口持有该事项的未删除快照尝试写回，墓碑在锁内及合并时强制压制并物理丢弃该事项；
   - **墓碑影响**：永久拦截该 `occasionId` 的再次插入与复活。

---

## 二、跨窗口墓碑合并与容量治理

1. **确定性合并规则（mergeOccasionCompletions）**：
   - 提取双方 `tombstones` 并集并去重归一化；
   - 派生 `deletedIds = Set(tombstone.occasionId)`；
   - 对双方持有的事项列表执行过滤：凡 `deletedIds.has(item.id)` 的条目一律直接物理丢弃；
   - 远端独有事项仅在未命中本地墓碑时才被安全采纳。
2. **墓碑硬容量上限（240 条）**：
   - 避免无限制删除导致存储膨胀；
   - 事项属于低频低容量实体（通常用户维持 10～50 项）；
   - 墓碑上限设为 **240 条**，超出时按 `deletedAt` 升序截断最旧墓碑。
3. **Upsert 强校验拦截**：
   - 在 `upsertOccasion` 写入层，如果目标 ID 命中现有墓碑，直接短路返回原 store，坚决杜绝代码逻辑错误导致的僵尸复活。

---

## 三、与主 Store 打卡事实的隔离红线

1. **单向引用原则**：
   - 事项可以关联打卡项目（`linkedOccasionId`），但打卡项目的主记录、规则与历史事件存储在独立的 `checkin-store` 中；
   - **事项删除绝不删除主 Store 关联项目与打卡事件**：事项删除只解除事项层面的提醒与展示，用户通过该事项积累的打卡成就、连击与打卡日志依然受到事实不可变红线保护；
2. **关联徽章自动降级**：
   - 事项删除后，其 ID 进入墓碑，关联项目在下一次重新绑定时自然识别为无关联事项，界面不留死链接。
3. **提醒协同清理**：
   - 事项删除后，由该事项派生的待办与提醒在投影层立即失效，历史完成日不再触发任何新提醒。
